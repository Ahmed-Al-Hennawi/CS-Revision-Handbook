Computer Science & Software Engineering — The Graduate Revision Handbook

Edition: October 2026
Audience: A computer science graduate refreshing fundamentals for junior software engineer, web developer, full-stack, QA, technical support, and graduate technical interviews.
How to use it: Read a chapter, run its code, explain the idea aloud without looking, then attempt the end-of-book assessment. Understanding beats memorising definitions.

Scope: Computer science is far too large to master from one guide. This handbook deliberately covers the core concepts you should recognise, explain and apply at entry level, plus the most common extensions. Specialised roles require additional depth. You do not need perfect recall to apply for graduate jobs.

Your study map

Priority A — explain confidently: how computers work; variables, loops, functions; OOP; arrays/maps/sets; Big O; SQL; HTML/CSS/JS; HTTP/API; Git; testing; security basics.
Priority B — implement in a small project: async code; frameworks; backend; auth; indexes; Docker; CI/CD; Linux; debugging.
Priority C — know at interview level: algorithms, operating systems, networking, system design, architecture, concurrency, cloud and AI fundamentals.

Suggested schedule: On each study day, revise 2–3 chapters and write code for at least 45 minutes. Use the chapter drills and do the final assessment closed-book. Revisit missed concepts after 1, 3 and 7 days. A thorough pass may take several weeks; use this as a permanent reference rather than a promise of instant mastery.

PART I — THE COMPUTER SCIENCE MENTAL MODEL

01. What actually happens when software runs?

Hardware is the physical machine. Software is instructions and data. The operating system (OS) manages processes, memory, storage and devices. An application runs on top of the OS and asks it for services.

  • CPU: executes instructions. A CPU has multiple cores; each core can execute work, while the OS schedules many tasks across them.
  • RAM: fast, working storage for programs and their data. Usually volatile: its contents disappear when power is removed.
  • SSD/HDD: persistent files, including code, apps and databases. Slower than RAM, but stores data after restart.
  • GPU: specialised parallel computation useful for graphics and AI workloads, not simply “a better CPU.”
  • Input / output: keyboard, network, display, disk. A program may spend much of its time waiting for I/O.
  • Binary: computers represent data with bits (0 or 1). Eight bits make one byte. Text is encoded into bytes (often UTF-8); an image and a sound file are also encoded data.

Example: You open a photo-editing app. Its executable is read from storage into memory, the CPU executes instructions, the GPU helps render the image, and saving writes modified data back to persistent storage.

Terms worth knowing: program = instructions on disk; process = running program with resources and address space; thread = a path of execution within a process; file = a named unit of stored bytes; filesystem = organisation of files/directories.

Interview: “RAM vs storage?” → RAM stores active working data, while persistent storage keeps data across restarts; RAM is generally faster and smaller.

Try it: Explain what happens between double-clicking an application and seeing its first window. Mention CPU, memory, OS and storage.

02. How is code translated into something that runs?

A programming language expresses instructions. A compiler typically translates source code into lower-level code ahead of execution (for example, C to machine code). An interpreter/runtime executes code through its execution environment. Many real languages use hybrid approaches: Python compiles source to bytecode for a virtual machine; Java typically compiles to JVM bytecode with runtime JIT compilation; JavaScript engines parse and optimise code and often JIT-compile it.

  • Syntax error: code breaks the grammar, such as a missing : in Python.
  • Runtime error: code is syntactically valid but fails while running, such as division by zero.
  • Logic bug: code runs but produces an incorrect answer.
  • Library: reusable code called from your program; framework: a larger structure that calls your code at defined points.
  • SDK: tools/libraries/docs for building a particular type of app; API: contract through which software communicates.
  • IDE vs editor: an IDE includes tools such as debuggers and project support; VS Code is primarily an extensible code editor.

Example (Python):

price = 20
quantity = 3
print(price * quantity)  # 60; prints the evaluated expression

Interview: “Compiler vs interpreter?” → They are approaches to translating and executing programs; modern language runtimes often use both techniques.

03. Types, memory, and the fundamentals of data

Variable = a name referring to a value. Type describes what operations a value supports. Common types: integer 42, float 3.14, Boolean True, string "hello", null/None (no value), collections, and objects.

Static typing checks many type rules before running (e.g., Java, TypeScript); dynamic typing checks types as code runs (e.g., Python, JavaScript). These are not the same thing as strong/weak typing. TypeScript's checks are erased when compiling to JavaScript, so validate external inputs at runtime.

Mutable objects can change after creation (Python list, dict); immutable objects cannot be mutated (Python int, str, tuple). A const variable in JavaScript cannot be reassigned, but an object referenced by const can still be mutated.

Stack and heap: a useful mental model is that short-lived function call frames often live on a call stack, while dynamically allocated objects may live on a heap. Exact storage details vary by language and runtime; don't assume every language stores every primitive on a stack.

Value vs reference: two names may refer to the same mutable object:

first = [1, 2]
second = first
second.append(3)
print(first)    # [1, 2, 3] — both refer to one list
copy = first.copy()
copy.append(4)
print(first)    # [1, 2, 3] — shallow list copy is separate

Interview: “== versus is in Python?” → == tests value equality; is tests identity. For checking None, use value is None.

04. Programming logic: conditions, loops, functions, scope

Conditionals choose branches; loops repeat work; functions package reusable logic and return results. Scope determines where a name can be accessed. Parameters are names in a function signature; arguments are the actual values passed.

def shipping_cost(total: float, is_member: bool) -> float:
    if is_member or total >= 50:
        return 0.0
    return 4.99

cart_totals = [19.0, 60.0, 8.0]
for total in cart_totals:
    print(shipping_cost(total, is_member=False))
# 4.99, 0.0, 4.99
  • if / elif / else branch on a condition.
  • for iterates over items; while repeats while a condition holds.
  • break exits a loop; continue skips to the next iteration.
  • Return sends a result and exits a function; printing only displays text.
  • Pure function: output depends only on its inputs and it has no observable side effects. Easier to test.
  • Recursion: a function calls itself with a smaller input and a base case to stop.

Example recursion:

def factorial(n):
    if n < 0:
        raise ValueError('n must be nonnegative')
    if n <= 1:
        return 1
    return n * factorial(n - 1)

print(factorial(4))  # 24

Interview: “Why use functions?” → Readability, reuse, separation of responsibilities, testing and maintainability. A good function has a clear purpose and interface.

05. Error handling, modules and good coding habits

Your code must expect failures: missing files, unavailable servers, malformed input and programming bugs. An exception signals an error; handle exceptions narrowly rather than silently swallowing everything.

def parse_age(text):
    try:
        age = int(text)
    except ValueError:
        return None
    return age if age >= 0 else None

print(parse_age('25'))      # 25
print(parse_age('unknown')) # None

Module: reusable source file that can be imported. Package: group of modules. Dependency: external code your project needs. Virtual environment: isolated Python environment for dependencies. Lockfile: records resolved dependency versions for reproducible installs. Never hardcode secrets in source code; use environment variables or secrets management.

Readable code: descriptive names, small functions, explicit input checks, meaningful errors, consistent formatting, and comments explaining why rather than repeating what. DRY = avoid duplicated business logic; KISS = avoid needless complexity; YAGNI = don't build unused features.

Try it: Write average(numbers) returning None for an empty list, and write tests for both ordinary and empty input.

PART II — HOW SOFTWARE IS STRUCTURED

06. Object-oriented programming (OOP)

A class defines a blueprint; an object is an instance with state (attributes) and behaviour (methods). OOP is one tool for organising larger applications; it is not required for every task.

class BankAccount:
    def __init__(self, owner: str, balance: float = 0):
        self.owner = owner
        self._balance = balance

    def deposit(self, amount: float):
        if amount <= 0:
            raise ValueError('Amount must be positive')
        self._balance += amount

    @property
    def balance(self):
        return self._balance

account = BankAccount('Sam', 100)
account.deposit(25)
print(account.balance)  # 125

The four classic OOP principles:

  1. Encapsulation: keep related state and behaviour together; expose a safe interface. _balance in Python is a convention, not truly private access control.
  2. Abstraction: hide implementation details behind a useful interface. A .deposit() method hides how the balance is stored.
  3. Inheritance: a class extends/reuses behaviour from another; e.g. ElectricCar(Car). Avoid complex hierarchies when composition is simpler.
  4. Polymorphism: different types respond to the same operation, e.g. Dog.speak() and Cat.speak().

Composition vs inheritance: a Car has an Engine (composition); a Car is a Vehicle (possible inheritance). Prefer composition when a simple relationship is sufficient.

Interface vs abstract class: an interface specifies a contract; abstract classes can also share state or implementation. Details depend on language. Dependency injection passes collaborators into a component rather than creating them internally, making testing easier.

SOLID in plain English:

  • S — Single Responsibility: a class or module has one cohesive reason to change.
  • O — Open/Closed: allow new behaviour with limited changes to stable code, often through extension.
  • L — Liskov Substitution: a subtype should honour the contract expected of its base type.
  • I — Interface Segregation: don't force clients to depend on operations they don't need.
  • D — Dependency Inversion: depend on stable abstractions rather than concrete implementations.

Interview: “Explain abstraction and encapsulation.” → Abstraction hides complexity behind a simple contract; encapsulation protects/manages state and behaviour inside a boundary.

07. Data structures: choosing how to store information

A data structure organises values for particular operations. The choice matters because searching, inserting and deleting have different costs.

Structure Mental model Typical operation cost Example
Array/list Ordered sequence Index O(1); search O(n); append amortised O(1) for dynamic arrays Shopping cart
Linked list Nodes connected by references Index/search O(n); insert/delete O(1) given the node Undo-chain concept
Stack Last in, first out (LIFO) Push/pop O(1) Undo, call stack
Queue First in, first out (FIFO) Enqueue/dequeue O(1) with appropriate structure Print jobs
Hash map/dictionary Key → value Expected lookup/insert O(1), worst case may differ User ID → user
Set Collection of distinct values Expected membership O(1) Unique usernames
Tree Parent/child hierarchy Depends on type and balance Folder tree
Heap/priority queue Fast access to min/max priority Peek O(1), insert/remove O(log n) Scheduling
Graph Nodes and connecting edges Traversal O(V+E) Social links, routes

Important nuance: Python's list is a dynamic array, not a linked list. For efficient queues use collections.deque; for a min-heap use heapq.

from collections import deque
from heapq import heappush, heappop

seen = {'Ada', 'Sam'}         # set
prices = {'apple': 2.5}      # dictionary / hash map
jobs = deque(['first'])
jobs.append('second')
print(jobs.popleft())         # first — FIFO

heap = []
heappush(heap, (1, 'urgent'))
heappush(heap, (5, 'normal'))
print(heappop(heap))          # (1, 'urgent')

Interview: “When do you use a set instead of a list?” → When you care about uniqueness or fast expected membership tests rather than preserving duplicates or indexed access.

08. Algorithms and Big O notation

An algorithm is a clear method for solving a problem. Time complexity describes how running time grows with input size; space complexity describes additional memory required. Big O commonly expresses an asymptotic upper bound, often discussed in worst-case terms. It is not a wall-clock time prediction.

Complexity Growth intuition Typical example
O(1) Roughly constant Array indexing
O(log n) Repeatedly halve Binary search in sorted array
O(n) Scan once Find max in unsorted list
O(n log n) Efficient comparison sorting Merge sort
O(n²) Nested scan Compare all pairs
O(2ⁿ) Rapid exponential growth Naive exhaustive subset enumeration

Linear search vs binary search:

def linear_search(items, target):
    for i, value in enumerate(items):
        if value == target:
            return i
    return -1                 # O(n)


def binary_search(sorted_items, target):
    left, right = 0, len(sorted_items) - 1
    while left <= right:
        mid = (left + right) // 2
        if sorted_items[mid] == target:
            return mid
        if sorted_items[mid] < target:
            left = mid + 1
        else:
            right = mid - 1
    return -1                 # O(log n); input MUST be sorted

Sort algorithms: bubble sort O(n²) average/worst; merge sort O(n log n) worst with O(n) auxiliary memory; quicksort O(n log n) average, O(n²) worst with poor pivots. Built-in sort is usually preferable in production.

Common problem-solving patterns:

  • Two pointers: check opposite ends of a sorted array or palindrome.
  • Sliding window: rolling maximum/count over contiguous ranges.
  • Hashing: count occurrences or find complements (two-sum).
  • BFS: explore graph layer by layer with a queue; shortest path in an unweighted graph.
  • DFS: explore deeply with recursion or stack; traversals and cycle detection.
  • Binary search: repeatedly narrow an ordered space, not just arrays.
  • Dynamic programming: store answers to overlapping subproblems, as in Fibonacci or coin change.
  • Greedy: pick the best apparent local option when a proof makes it safe; not all problems permit this.
  • Backtracking: explore choices, undo choices, and prune invalid paths.

Two-sum example (O(n) expected time, O(n) extra space):

def two_sum(nums, target):
    seen = {}
    for i, num in enumerate(nums):
        needed = target - num
        if needed in seen:
            return [seen[needed], i]
        seen[num] = i
    return []

print(two_sum([2, 7, 11, 15], 9))  # [0, 1]

Interview: Speak through brute force first, estimate complexity, improve it, then test edge cases. An answer that works and is clearly explained is usually better than silent clever code.

09. More algorithms you should recognise

Binary trees: each node has at most two children. Binary search trees (BSTs) keep smaller keys to the left and larger to the right; balanced trees commonly support O(log n) search, but a skewed BST can degrade to O(n). Traversals: preorder (node/left/right), inorder (left/node/right), postorder (left/right/node). Inorder of a BST gives sorted keys.

Graph representation: adjacency list {'A': ['B','C']} is compact for sparse graphs; adjacency matrix is a square table of potential edges. Dijkstra's algorithm finds shortest paths when edge weights are nonnegative. Topological sort orders dependencies in a directed acyclic graph (DAG); think build steps or prerequisite courses.

Hash collisions: two keys can map to the same bucket; hash tables need a collision-handling strategy. Typical average O(1) performance depends on healthy hashing and load factor.

Recursion vs iteration: recursion can simplify tree code, but deep recursion may exhaust call stack space. Iteration with explicit stack/queue avoids that limit for some tasks.

Example BFS:

from collections import deque

def bfs(graph, start):
    visited = {start}
    queue = deque([start])
    order = []
    while queue:
        node = queue.popleft()
        order.append(node)
        for neighbour in graph.get(node, []):
            if neighbour not in visited:
                visited.add(neighbour)
                queue.append(neighbour)
    return order

print(bfs({'A': ['B','C'], 'B': ['D'], 'C': [], 'D': []}, 'A'))
# ['A', 'B', 'C', 'D']

Practice: Explain how you would detect duplicate email addresses in a million records, and compare a nested-loop O(n²) method with a hash-set O(n) expected method.

PART III — DATABASES AND DATA

10. Relational databases and SQL from zero

A database stores and retrieves organised data; a DBMS (PostgreSQL, MySQL, SQLite, etc.) manages it. A relational database stores rows in tables and connects tables using keys.

  • Table: entity collection, e.g. users. Row: one record. Column: one attribute.
  • Primary key (PK): unique identifier, typically non-null.
  • Foreign key (FK): refers to a key in another table; enforces referential integrity where constraints are enabled.
  • Schema: structure, types, constraints and relationships.
  • NULL: missing/unknown value, not zero or empty string. Use IS NULL, not = NULL.

Example schema:

CREATE TABLE customers (
    id INTEGER PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL
);
CREATE TABLE orders (
    id INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL REFERENCES customers(id),
    total DECIMAL(10,2) NOT NULL CHECK (total >= 0)
);

CRUD: Create (INSERT), Read (SELECT), Update (UPDATE), Delete (DELETE). A WHERE clause limits rows; forgetting it in UPDATE or DELETE can affect every row.

INSERT INTO customers (id, name, email)
VALUES (1, 'Ada', 'ada@example.com');

SELECT id, name FROM customers WHERE name LIKE 'A%';
UPDATE customers SET name = 'Ada Lovelace' WHERE id = 1;
DELETE FROM customers WHERE id = 1;

Example table orders: [(10, 1, 75), (11, 1, 25), (12, 2, 30)] where values are (id, customer_id, total).

SELECT customer_id, COUNT(*) AS order_count, SUM(total) AS spent
FROM orders
WHERE total > 0
GROUP BY customer_id
HAVING SUM(total) >= 50
ORDER BY spent DESC;

SQL's conceptual stages are approximately FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT, although DB optimisers may execute differently. WHERE filters source rows; HAVING filters aggregated groups. DISTINCT removes duplicate result rows. LIMIT/OFFSET page results (syntax varies by database).

Joins:

SELECT c.name, o.id, o.total
FROM customers AS c
INNER JOIN orders AS o ON c.id = o.customer_id;
  • INNER JOIN: only matching rows on both sides.
  • LEFT JOIN: all left rows, and matching right rows (otherwise NULLs).
  • RIGHT JOIN: reverse of left (not supported in all systems).
  • FULL OUTER JOIN: rows from both sides whether matched or not (not all systems).
  • CROSS JOIN: all combinations; can be huge.

Interview: “WHERE vs HAVING?” → WHERE acts before aggregation; HAVING filters grouped/aggregated results.

11. Database design, indexes, transactions

Normalisation reduces unnecessary duplication and update anomalies. 1NF: atomic field values. 2NF: attributes depend on the full candidate key, not part of a composite key. 3NF: non-key attributes do not depend transitively on a key through another non-key attribute. In practice, separating customers and orders avoids repeating customer emails on every order.

Index: a data structure (often B-tree) accelerating lookup and sorting for suitable queries, at a cost of storage and slower writes. Indexing orders(customer_id) can improve retrieving a customer's orders; indexes are not automatically helpful for every query. Use EXPLAIN/query plans and realistic data.

Transactions group operations atomically. Transfer example:

BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 1;
UPDATE accounts SET balance = balance + 50 WHERE id = 2;
COMMIT;
-- On an error, ROLLBACK; also validate balances / affected rows.

ACID: Atomicity all-or-nothing; Consistency rules preserved; Isolation simultaneous transactions behave according to the chosen isolation level; Durability committed data survives failures as promised by the DBMS. Isolation levels trade performance and anomalies. Transactions alone do not replace constraints or good application logic.

N+1 query problem: fetching 100 orders then querying their customer once each makes 101 DB queries. A JOIN or batch fetch can reduce the round trips.

Migrations: version-controlled changes to schema. Backups: recover lost data; a replica does not automatically replace backups. Optimistic locking: detect concurrent edits with version numbers; pessimistic locking: lock selected resources.

Interview: “How do you make a slow query faster?” → Reproduce with real data, inspect its query plan, identify excessive scans/joins, evaluate indexes and query shape, benchmark, then review tradeoffs.

12. NoSQL, JSON, caching and data formats

NoSQL includes document, key–value, wide-column and graph databases. It does not mean “has no query language.” MongoDB is a document database where a record can resemble JSON. Redis is commonly a fast in-memory data store/cache. SQL refers to a language for relational queries, not MongoDB's default query API.

// MongoDB shell example
// Find active users at least 18 years old:
db.users.find({ active: true, age: { $gte: 18 } })

SQL vs document databases: relational databases shine when relationships, joins and multi-row constraints matter. Document databases fit some flexible, document-centric access patterns. Neither is automatically faster: choose based on queries, consistency requirements, operations and data model.

JSON is a text format for exchange; keys and string values use double quotes; supported values include object, array, number, string, boolean and null. A JSON document isn't the same as a JavaScript object in memory.

{"id": 7, "skills": ["Python", "SQL"], "available": true}

Cache: temporarily store data that is expensive to compute/fetch. Example: cache a product list for 60 seconds. Tradeoff: stale content and invalidation challenges. Cache-aside: read cache, and on a miss fetch database then write cache. TTL: time-to-live before expiry.

Interview: “Would you use SQL or MongoDB?” → Start with data relationships, required transactions, query patterns, scale, operational experience and team needs; explain a tradeoff instead of declaring a universal winner.

PART IV — WEB DEVELOPMENT, NETWORKS AND APIs

13. How the internet and web actually work

Internet: interconnected networks that move packets using standard protocols. Web: one application system built on top of it, using browsers, URLs and HTTP/HTTPS.

When you type https://example.com/products:

  1. The browser parses the URL and may look in caches.
  2. DNS finds the service address (often an IP address), possibly through multiple lookup steps.
  3. The client establishes a connection (TCP + TLS for common HTTPS setups; HTTP/3 uses QUIC over UDP instead).
  4. The browser sends an HTTP request to the server/CDN.
  5. Server software reads data or talks to services/databases, returning an HTTP response.
  6. Browser parses HTML into a DOM, CSS into styling rules, executes JavaScript, and renders pixels; further asset/API requests may follow.

IP address: network-layer address. Port: identifies a service endpoint at a host. DNS: hostname resolution. TCP: reliable ordered byte stream. UDP: datagrams without TCP's reliability guarantee. TLS: encrypted authenticated connection. HTTPS: HTTP protected using TLS (or equivalent HTTP/3 transport integration).

Client/server: browser or mobile app is the client; server accepts requests. Frontend: interface in browser. Backend: server-side logic. Database: persistent store. CDN: distributed caches close to users. Reverse proxy: accepts inbound traffic and forwards it to application servers. Load balancer: distributes requests across instances.

Interview: “What happens when you enter a URL?” → DNS, connection/TLS, HTTP request, backend response, browser parsing/rendering and additional requests. Name caching and asynchronous loading if appropriate.

14. HTTP and REST APIs

Request: method + URL + headers + optional body. Response: status + headers + optional body.

GET /api/products/7 HTTP/1.1
Host: example.com
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json

{"id":7,"name":"Laptop","price":899}

Common methods: GET retrieve; POST submit/create/action; PUT replace a resource; PATCH partially modify; DELETE remove. GET and PUT are idempotent by HTTP semantics: repeating the same request has the same intended effect on server state (not necessarily identical response); POST is not guaranteed idempotent.

Status Meaning Example
200 OK Read succeeded
201 Created New resource
204 No Content Successful delete
400 Bad Request Invalid request
401 Unauthorized (authentication needed/invalid) Not logged in
403 Forbidden Authenticated but not allowed
404 Not Found Unknown path/id
409 Conflict Duplicate or conflicting state
429 Too Many Requests Rate limited
500 Internal Server Error Backend fault
503 Service Unavailable Temporarily down

REST is an architectural style that models resources, uses a uniform HTTP interface and keeps requests stateless in the relevant sense; many real-world “REST APIs” implement a subset. GraphQL: client specifies desired data shape, usually through a schema and queries. WebSocket: persistent bidirectional communication suitable for chat/live status. Polling: repeated requests at intervals. Webhook: one service calls your endpoint when an event happens.

Pagination: avoid sending a million records in one response. Offset paging is easy but can shift when rows change; cursor/keyset paging is often better for large, changing collections. API versioning: manage incompatible interface changes. Rate limiting: protect service capacity/abuse. CORS: a browser-enforced mechanism controlling access to cross-origin responses; it is not authentication and does not stop server-to-server traffic.

Interview: “401 vs 403?” → 401 usually means missing/invalid credentials; 403 means the request is understood but the user is not permitted.

15. HTML, CSS, responsive design and accessibility

HTML describes content and meaning; CSS controls presentation; JavaScript provides behaviour.

<main>
  <h1>Contact us</h1>
  <form action="/contact" method="post">
    <label for="email">Email</label>
    <input id="email" name="email" type="email" required>
    <button type="submit">Send</button>
  </form>
</main>

Semantic HTML: prefer <header>, <nav>, <main>, <section>, <article>, <button> over arbitrary <div> elements for every role. Proper labels connect inputs to their purposes. alt text describes meaningful images; decorative images may have empty alt. Keyboard navigation, sufficient contrast and focus indicators are important for accessibility.

CSS box model: content + padding + border + margin. box-sizing: border-box includes content, padding and border in the specified width. Specificity resolves conflicting selectors; cascade also considers origin, layers and source order. Flexbox = one-dimensional layout; Grid = two-dimensional layout. Media queries adapt layouts to screen sizes.

* { box-sizing: border-box; }
.cards { display: grid; grid-template-columns: repeat(3, 1fr); gap: 1rem; }
@media (max-width: 700px) {
  .cards { grid-template-columns: 1fr; }
}

Responsive means layouts adapt well to device/viewports; accessible means interfaces can be used by people with varied abilities and tools. An attractive website can still be inaccessible.

Interview: “id vs class?” → id identifies a unique element in a document; class groups any number of elements for styling and JS selection.

16. JavaScript and TypeScript fundamentals

JavaScript runs in browsers and server environments such as Node.js. It is dynamically typed, has first-class functions, closures, prototypes and an event loop.

const price = 10;    // cannot reassign the binding
let quantity = 3;    // can reassign
const cart = [1, 2];
cart.push(3);        // allowed: const doesn't freeze the array

const square = (n) => n * n;
const doubled = cart.map((n) => n * 2);  // [2, 4, 6]
const even = cart.filter((n) => n % 2 === 0); // [2]

=== checks strict equality without type coercion in most ordinary cases; prefer it to loose == unless coercion is deliberate. null represents intentional absence; undefined often means a value has not been supplied. map transforms elements; filter selects; reduce combines. Destructuring, spread syntax and template literals are common syntax.

Closure: an inner function retains access to bindings from its enclosing scope:

function makeCounter() {
  let count = 0;
  return () => ++count;
}
const next = makeCounter();
console.log(next(), next()); // 1, 2

Asynchronous programming: a Promise represents eventual completion/failure. async/await lets you write promise-based code in a readable style. It doesn't mean the whole JavaScript program pauses while waiting. Network I/O runs asynchronously and completed callbacks are scheduled through the runtime's event loop.

async function getUser(id) {
  const response = await fetch(`/api/users/${id}`);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return await response.json();
}

fetch does not reject its Promise merely because the server returned HTTP 404/500; check response.ok. Promise.all waits for multiple promises, rejecting if any reject; Promise.allSettled reports each outcome.

TypeScript adds static type checking and useful tooling to JavaScript. It compiles to JavaScript and does not validate untrusted JSON by itself:

Interview: “let vs const vs var?” → let is reassignable and block-scoped; const is block-scoped and prevents rebinding; var is function-scoped with hoisting behaviour. Prefer const by default, let when reassignment is needed.

17. Frontend frameworks and component thinking

A framework/library like React helps break the UI into reusable components and update the interface when state changes. The DOM is the browser's in-memory representation of document nodes; React renders a virtual representation and reconciles updates to the DOM.

import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(c => c + 1)}>Count: {count}</button>;
}
  • Props: read-only inputs passed from parent to component.
  • State: data that may change and trigger rendering.
  • Event handler: code run after an interaction.
  • Effect: synchronise with external systems, not simply a place for all business logic.
  • Controlled form: input value is driven by application state.
  • SPA: client changes displayed views without fetching an entirely new HTML document for every navigation.
  • SSR: server produces initial HTML; hydration connects client JavaScript to interactive UI.

State location: Keep state close to components that need it; lift state up when siblings share it; use global state only when appropriate. Keys: stable IDs help correctly track items in lists; array indices can be unsafe for reorderable lists.

Interview: “What causes a React rerender?” → State/prop/context-related updates and parent rendering can cause component functions to rerun; React then decides what DOM changes are needed.

18. Backend services and an end-to-end application

A backend validates requests, checks identity/permissions, runs business rules, reads/writes data and returns responses. A good backend does not trust browser input merely because an HTML form validated it.

Example simplified FastAPI service (Python):

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field

app = FastAPI()
products = {1: {"id": 1, "name": "Bottle", "price": 12.0}}

class ProductIn(BaseModel):
    name: str
    price: float = Field(ge=0)

@app.get('/products/{product_id}')
def get_product(product_id: int):
    product = products.get(product_id)
    if product is None:
        raise HTTPException(status_code=404, detail='Not found')
    return product

@app.post('/products', status_code=201)
def add_product(product: ProductIn):
    new_id = max(products, default=0) + 1
    saved = {"id": new_id, **product.model_dump()}
    products[new_id] = saved
    return saved

This is for learning only: in-memory data disappears on restart and isn't safe for concurrent production writes. A production version would use a database, authentication and authorization as needed, error handling and observability. Run via an appropriate ASGI server such as uvicorn main:app --reload after installing dependencies.

Layered architecture: route/controller receives request → service applies business rules → repository/data access reads/writes database → result is serialised to response. The goal is separation of responsibilities, not “more folders.”

Interview: “Frontend vs backend?” → Frontend owns the user interaction and display; backend performs trusted business/data operations. Both validate for different reasons: UX vs security/integrity.

PART V — SYSTEMS, SECURITY, DELIVERY

19. Operating systems, processes and the terminal

A process has its own virtual address space and resources. Threads in one process share much of the process memory. Concurrency is managing multiple tasks in overlapping periods; parallelism is literally executing tasks at the same time on different processing resources. Context switching saves/restores execution state. A race condition depends on uncontrolled timing between operations.

CPU-bound vs I/O-bound: CPU-bound work spends time computing, such as video encoding; I/O-bound work waits on network or disk. Async I/O shines for high-concurrency waiting, while CPU-heavy jobs may benefit from multiprocessing, native parallelism or worker queues.

Deadlock: two or more tasks wait indefinitely on resources held by each other. Avoid with consistent lock ordering, timeouts and minimal critical sections. Mutex: allows one thread/task into a critical section. Semaphore: permits a limited number of concurrent entrants.

Unix/macOS terminal essentials:

pwd                     # current directory
ls -la                  # list including hidden files
cd ~/Documents           # change directory
mkdir demo               # create directory
cp source.txt copy.txt   # copy a file
mv copy.txt newname.txt  # rename/move
cat newname.txt          # print file contents
grep -n "error" app.log   # find matching lines
ps aux                  # list processes
kill 12345              # send termination signal to a PID
python3 -m venv .venv   # create Python virtual env
source .venv/bin/activate

Paths: absolute /Users/sam/project vs relative ./project. Environment variables: configuration passed into processes (e.g. PORT), but shell history and logs can expose secrets if handled carelessly. Permissions: read/write/execute and ownership; least privilege means grant only required access. Never run unfamiliar curl ... | bash commands without verifying them.

Interview: “Process vs thread?” → Separate processes are generally more isolated and have separate address spaces; threads in a process share memory and need careful synchronisation.

20. Security and privacy fundamentals

CIA triad: confidentiality (only authorised readers), integrity (data isn't improperly altered), availability (service remains accessible). Authentication asks who are you?; authorization asks are you allowed to do this?. Always enforce authorization on the server for each resource/action.

Password security: never store plaintext passwords; use a slow password-hashing algorithm designed for passwords such as Argon2id or bcrypt, with unique salts and appropriate configuration. Hashing is one-way; encryption is reversible using keys. TLS protects data in transit. Rotate/secure secrets, keep dependencies patched, use MFA where suitable.

SQL injection happens when untrusted input changes a query's syntax. Use parameterised queries, never concatenate input into SQL commands:

# GOOD: placeholder / parameters; syntax varies by DB driver
cursor.execute('SELECT * FROM users WHERE email = ?', (email,))

# BAD: input becomes executable SQL syntax
# cursor.execute("SELECT * FROM users WHERE email = '" + email + "'")

XSS: attacker-provided content executes as script in another user's browser; escape/encode according to output context, use safe templating APIs and Content Security Policy as defence in depth. CSRF: tricks a browser into sending an unwanted authenticated action; mitigate with SameSite cookies, CSRF tokens and suitable checks. Broken access control/IDOR: changing /orders/42 to /orders/43 must not reveal another user's order. SSRF: backend is tricked into contacting unwanted destinations. Security misconfiguration: exposed admin panels, default passwords, verbose errors.

Cookies vs localStorage: cookies can be HttpOnly, Secure and SameSite; localStorage is readable by page JavaScript, so tokens stored there may be exposed by XSS. Neither storage approach fixes poor authorization. Session: a server-managed login state referenced by cookie/session ID. JWT: signed token format with claims; signature verification and expiry validation matter, and a JWT is not automatically encrypted or safer.

2025 OWASP Top 10 reminder: Broken Access Control, Security Misconfiguration, Software Supply Chain Failures, Cryptographic Failures, Injection, Insecure Design, Authentication Failures, Software or Data Integrity Failures, Security Logging & Alerting Failures, and Mishandling of Exceptional Conditions. Names and rankings evolve; use the official current OWASP list.

Interview: “How do you protect an API?” → HTTPS, authentication, object-level authorization, input validation, parameterised queries, rate limiting, secure secret handling, logging, dependency updates, testing and monitoring.

Git: distributed version-control system on your machine. GitHub/GitLab: hosting/collaboration platforms using Git. Commit: snapshot of changes with a message. Branch: independent line of development. Merge: integrate history. Pull request (PR): request review before merging; not a native Git command.

22. Testing, debugging and code quality

Unit tests: small pieces in isolation. Integration tests: multiple components working together, e.g. API plus DB. End-to-end (E2E): whole user flow. Regression test: catches a bug that was previously fixed. Smoke test: quick check key functionality works.

# app.py
def discount(price, percent):
    if price < 0 or not 0 <= percent <= 100:
        raise ValueError('Invalid input')
    return round(price * (1 - percent / 100), 2)

# test_app.py (pytest)
import pytest
from app import discount

def test_discount():
    assert discount(100, 20) == 80

def test_bad_price():
    with pytest.raises(ValueError):
        discount(-1, 10)

Test design: normal case, boundary (0, empty list, last element), invalid input, permissions, failures, concurrency. Test doubles: mocks/stubs replace dependencies when appropriate. Test pyramid: many fast unit tests, fewer integration/E2E tests as a rough guide; exact balance varies. Coverage: measures code executed, not correctness. TDD: red failing test → green minimal implementation → refactor.

Debugging routine: 1) reproduce, 2) reduce to smallest failing case, 3) inspect logs/traceback, 4) form a hypothesis, 5) inspect state with breakpoints, 6) fix cause not symptom, 7) regression-test. Logs should help diagnose errors without exposing secrets or private information.

Static analysis checks source without running it; linter flags suspicious patterns/style; formatter applies consistent layout; type checker catches type inconsistencies; code review surfaces defects and helps knowledge sharing.

Interview: “Unit vs integration vs E2E?” → Unit verifies small logic, integration verifies interfaces between real components, E2E checks a complete workflow.

23. SDLC, Agile and engineering workflow

Software Development Life Cycle (SDLC): requirements → design → implementation → testing → deployment → operations/maintenance; in practice the loop repeats continuously.

  • Requirement: what must the product do? Functional (“user can reset password”) vs non-functional (“page loads within SLO”).
  • User story: “As a user, I want X so I can Y.” Add acceptance criteria for a testable definition of done.
  • Agile: respond to feedback in increments; Scrum uses roles, timeboxed sprints and events; Kanban visualises work and limits work in progress. Not every team uses Scrum.
  • Ticket/issue: bounded item describing requested work, priority and acceptance criteria.
  • Code review: teammate checks changes before merging.
  • Technical debt: future cost caused by shortcuts or choices; some is intentional and managed.
  • Refactoring: change code structure without intentionally changing external behaviour.
  • Documentation: README, setup steps, API docs, architecture decisions and runbooks.

Example ticket: “Users can reset forgotten passwords. Done when an email with expiring one-time link can be requested; link is single-use; rate limiting exists; tests cover expired/invalid token.”

Interview: “What would you do if requirements are unclear?” → Ask about the user outcome, acceptance criteria, constraints and edge cases; propose a small testable version and confirm with stakeholder.

24. Cloud, containers and deployment

Cloud computing: rent compute/storage/services rather than owning hardware. IaaS: virtual machines and networks; PaaS: managed application runtime; SaaS: fully managed application. Region: geographic area for services; availability zone: physically separated infrastructure within a region (definitions vary by provider).

VM vs container: VM virtualises a full guest OS on a hypervisor; container packages an application and dependencies while sharing the host kernel through OS-level isolation. Docker image: immutable package template; container: running instance. Container orchestration systems such as Kubernetes manage deployment/scaling/networking across hosts.

For production, consider pinning dependencies and image digests, running as non-root, scanning images and excluding secrets from build contexts. CI (Continuous Integration): automatically run tests/checks on changes. CD: Continuous Delivery (ready to deploy) or Continuous Deployment (automatic production deployment), depending on team.

Simple pipeline: push Git branch → build → lint/type check → unit/integration tests → security scan → package → deploy staging → validate → production. Blue-green/canary deployment reduce release risk. Rollback returns to a prior working version.

Monitoring: metrics (numbers over time), logs (events) and traces (request flow across services). Latency: time to complete a request. Throughput: requests per second. Availability: proportion of time service is usable. SLA: external service agreement; SLO: internal measurable reliability target; SLI: measured indicator.

Interview: “Your service crashes after deployment?” → Stop impact/roll back where appropriate, read health metrics/logs, compare release changes, reproduce, fix, test and document the incident.

25. Architecture and entry-level system design

Monolith: app is packaged/deployed as a unit; often excellent for a small team. Microservices: independently deployable services with explicit network boundaries; can scale teams/domains but add distributed systems complexity. Three-tier model: presentation, application/business logic and data. Queue: decouple slow jobs from a request (e.g., send email or process uploaded video asynchronously).

Design a simple URL shortener:

  1. Requirements: create short code, redirect to full URL, reject unsafe URLs, track clicks if desired.
  2. API: POST /links {url} → {code}; GET /{code} → redirect.
  3. Data: table links(code PRIMARY KEY, url, created_at); unique index on code.
  4. Flow: client → API → DB; optionally cache popular code-to-URL mappings.
  5. Reliability/security: collision handling, validation, rate limiting, safe redirects, monitoring.
  6. Scaling: load balancer + multiple stateless API instances; DB capacity/caching if real traffic justifies it.

Scale up (vertical): bigger machine. Scale out (horizontal): more instances. Replication: multiple copies, often for availability/reads; sharding: distribute distinct data across nodes. Eventual consistency: replicas may disagree temporarily before converging. CAP theorem: in a partitioned distributed system you must trade some availability against strong consistency for particular operations; it does not simply label databases as always “CP” or “AP” in all modes.

Reliability patterns: retries with exponential backoff/jitter for transient failures; timeouts; circuit breakers; idempotency keys for safe repeated payment-like operations. Avoid blindly retrying non-idempotent side effects.

Interview: For system design, start with users/requirements, data model, API, happy-path flow, bottlenecks, safety and tradeoffs—not a giant architecture diagram immediately.

26. Mathematics and technical foundations

  • Boolean logic: AND is true only when both inputs true; OR when at least one; NOT flips. Used in conditions, filters and circuits.
  • Base systems: binary 1010₂ = 10 decimal; hexadecimal 0xFF = 255 decimal. Useful for flags, debugging and networking.
  • Probability: likelihood between 0 and 1; critical for testing, ML and reasoning about reliability.

  • Discrete maths: sets, relations, graphs, counting, proof by induction. Useful for algorithms.
  • Linear algebra: vectors/matrices used in graphics, computer vision, machine learning.

27. AI, machine learning and computer vision (interview overview)

Artificial intelligence: broad effort to make systems carry out tasks associated with intelligent behaviour. Machine learning: learn patterns from data rather than manually coding all decisions. Deep learning: neural-network methods with many layers. Generative AI: models that produce new content. LLMs: language models trained to predict/generate sequences of tokens using learnt patterns; they can be useful and still produce errors.

Supervised learning: train with labels (spam/not spam). Unsupervised: find structure without those labels (customer clustering). Reinforcement learning: learn from actions and reward signals. Training set fits parameters; validation set guides model selection; test set estimates final generalisation. Data leakage: information from evaluation improperly reaches training, inflating results.

Overfitting: memorises training patterns, performs poorly on unseen data. Underfitting: model too simple or undertrained. Classification: predict class; regression: predict numeric value. Precision: TP/(TP+FP); recall: TP/(TP+FN); F1: harmonic mean of precision and recall. Confusion matrix: counts predictions vs true labels. Accuracy alone can mislead on imbalanced data.

Computer vision: extract information from images/video. A pose estimation model predicts body landmarks; a rule-based layer might compute knee angles and flag movement conditions. Pose tracking can fail due to occlusion, camera angle, lighting and model bias. Transparent feedback should state uncertainty and limitations, not imply medical certainty.

AI-assisted development: use models to brainstorm/tests/explain code, but verify output, protect secrets and private data, inspect licences, and understand what you submit. Interviewers may ask you to explain code you used AI to create.

29. How to tackle a live coding interview

Typical tasks to practise: reverse a string; palindrome; character frequency; remove duplicates; two-sum; valid parentheses; merge sorted arrays; binary search; first non-repeating character; longest substring without duplicates; BFS; detect linked-list cycle; group anagrams; SQL JOIN and GROUP BY; build a small REST endpoint; fix a broken asynchronous function.

Worked example — valid parentheses:

def valid_parentheses(text):
    pairs = {')': '(', ']': '[', '}': '{'}
    stack = []
    for ch in text:
        if ch in '([{':
            stack.append(ch)
        elif ch in pairs:
            if not stack or stack.pop() != pairs[ch]:
                return False
    return not stack

print(valid_parentheses('([])')) # True
print(valid_parentheses('([)]')) # False

Complexity: O(n) time; O(n) worst-case extra space. Boundary cases: empty string (valid here), a starting closing bracket, unexpected characters (currently ignored; specify whether allowed).

Interview behaviour: Say what you're thinking, own uncertainty, ask clarifying questions and admit when a solution is O(n²). Do not claim proficiency beyond what you can demonstrate.

P9:

SELECT c.id, c.name, SUM(o.total) AS spent
FROM customers c
JOIN orders o ON c.id = o.customer_id
GROUP BY c.id, c.name
HAVING SUM(o.total) > 100;

JOIN here is inner, so customers without orders do not appear. Use LEFT JOIN and COALESCE to include them, though an over-100 threshold still filters out zero totals.
